Contributing to Open Source

Issue tracking, pull requests, and code review — the workflow every real open-source project runs on, practiced on our own GitHub organization: CZMGC-SY202528.

Issue tracking

An issue is a tracked unit of work: a bug report, a feature request, or a task. Good issues are specific enough that someone else could pick them up without asking you questions first.

FieldPurpose
TitleShort, imperative — "Fix broken email validation," not "there's a bug somewhere"
DescriptionWhat's wrong or wanted, and how to reproduce or verify it
Labelsbug, enhancement, good first issue, etc.
AssigneeWho's doing the work

Branch → change → push

Never commit straight to main. Every contribution starts on its own branch:

git checkout main
git pull origin main                       # start from the latest

git checkout -b fix/email-validation
# ...make the change...
git add .
git commit -m "Add regex validation for email field"
git push -u origin fix/email-validation

Opening a pull request

A pull request (PR) is a diff-based proposal to merge your branch into main. Write the description so a reviewer understands what changed and why without reading the whole diff first:

## What
Adds regex-based email validation on the signup form

## Why
Closes #12

## How to test
1. Enter an invalid email
2. Confirm the error message appears
Tip Writing Closes #12 in the PR description links it to the issue — the issue closes automatically when the PR merges.

Code review

Reviewing is about correctness, readability, and shared understanding — not gatekeeping. A review ends in one of three states:

VerdictMeaning
CommentFeedback, no blocking opinion either way
Request changesSomething needs fixing before merge
ApproveSafe to merge — doesn't mean flawless, means good enough to ship and iterate on

Good review comments are specific and point to a line, and phrased as a question or suggestion rather than a command:

  • nit: minor/style — take it or leave it
  • question: genuinely asking, not a disguised objection
  • suggestion: a concrete alternative
  • blocking: this must change before merge

The full cycle on CZMGC-SY202528

Branch protection on your team repo requires a PR and at least one approval before anything reaches main — so this cycle isn't optional, it's how the repo works:

StepWhoAction
1Student AOpens an issue describing a bug/feature
2Student AAssigns it to Student B, adds a label
3Student BBranches, makes the change, pushes
4Student BOpens a PR with Closes #<n>
5Student AReviews — at least one question, one suggestion — then requests changes
6Student BPushes a follow-up commit addressing feedback
7Student AApproves
8EitherSquash & merge — issue auto-closes
Common mistake Forgetting Closes #12 in the PR — the issue won't auto-close on merge, and you'll have to close it by hand.

Quiz — check your understanding

1. What does writing "Closes #12" in a PR description do?
Correct — GitHub links and auto-closes the issue on merge.
Not quite — that phrasing is a GitHub convention that auto-closes the linked issue on merge.
2. What does "Request changes" mean during a review?
Correct.
Not quite — it's feedback that blocks merge until addressed, not a rejection.
3. Why does branch protection on main matter for this workflow?
Correct — it makes the issue → PR → review cycle mandatory rather than optional.
Not quite — branch protection enforces review before merge; it doesn't touch branching or issues directly.
4. What makes a good issue title?
Correct.
Not quite — a good title is specific enough that someone else could act on it without asking you first.
5. What does "Approve" mean on a PR?
Correct.
Not quite — approval means "good enough to ship," not "flawless."
