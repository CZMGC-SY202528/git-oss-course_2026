Git Fundamentals

Repositories, commits, branches, and merges — done entirely on your own machine, so the mental model is solid before GitHub enters the picture.

Git vs. GitHub

Git is the version control tool: it runs on your machine, works offline, and tracks every change you make. GitHub is a hosting service for Git repositories that adds collaboration features — issues, pull requests, code review. You'll use plain Git in this module and add GitHub in Module 2.

The three areas

Every file in a Git repository moves through three places:

AreaWhat it meansCommand that moves it here
Working directoryThe files you're editing right now— (you just save the file)
Staging areaChanges marked "ready to be committed"git add <file>
Repository (history)Permanent snapshotsgit commit -m "message"

Repositories & your first commits

# start tracking a folder
mkdir git-practice && cd git-practice
git init

# set your identity once per machine
git config --global user.name "Student Name"
git config --global user.email "student@example.com"

echo "# My Practice Repo" > README.md
git status                 # README.md is untracked
git add README.md
git status                 # README.md is staged
git commit -m "Initial commit: add README"
git log                    # see the commit
Try it Edit README.md again and run git diff before staging, then git diff --staged after. Watch how the same change appears in a different place depending on whether it's staged.

Branches

A branch is a movable pointer to a commit. main is just a branch by convention — nothing in Git treats it as special. Branching is cheap, so branch often.

git branch                        # list branches
git checkout -b feature/about     # create + switch in one step
echo "This project teaches Git." >> README.md
git add README.md
git commit -m "Add about section to README"
git log --oneline --graph --all   # visualize the branches diverging

Switch back with git checkout main — the change disappears from view, but it isn't lost. It's isolated on feature/about until you merge it.

Merging

git checkout main
git merge feature/about
git branch -d feature/about       # delete once merged

If main hasn't moved since the branch was created, this is a fast-forward merge — Git just slides the pointer forward. If both branches have new commits, Git creates a real merge commit with two parents.

Merge conflicts

A conflict happens when two branches change the same lines differently. Git can't guess which version you want, so it stops and asks:

<<<<<<< HEAD
your main branch's version
=======
the incoming branch's version
>>>>>>> feature/conflict

Edit the file to keep what you want, delete the marker lines, then:

git add README.md
git commit
Common mistake Panicking at a conflict. It's Git's normal behavior when two people (or two branches) touch the same line — not an error state. Read both versions, decide, remove the markers, commit.

Command reference

git init                            # start tracking a new folder
git clone <url>                     # copy a remote repo locally
git status                          # what's changed / staged
git add <file>   /   git add .      # stage changes
git commit -m "message"             # snapshot staged changes
git log --oneline --graph --all     # visual history

git branch                          # list branches
git checkout -b <name>              # create + switch
git branch -d <name>                # delete a merged branch
git merge <branch>                  # merge into current branch

Quiz — check your understanding

1. What does git add actually do?
Correct — staging marks a change as ready to commit; it isn't history yet.
Not quite — git add only stages the change; git commit saves it to history.
2. In Git, what is a branch?
Correct — a branch is just a lightweight, movable pointer. That's why branching is cheap.
Not quite — a branch doesn't copy anything; it's a pointer to a commit.
3. When does a merge conflict happen?
Correct — Git can auto-merge non-overlapping changes; conflicts only occur on overlapping edits.
Not quite — most merges are automatic. Conflicts only happen on overlapping line changes.
4. What's the difference between Git and GitHub?
Correct.
Not quite — Git works fully offline; GitHub adds hosting and collaboration on top.
5. Which command shows staged changes only?
Correct — git diff alone shows unstaged changes; add --staged to see what's staged.
Not quite — plain git diff shows unstaged changes. Add --staged for what's in the staging area.
